## Requirements
### Requirement: Stateful event reducer

The system SHALL provide `~/.claude/scripts/bin/audit-reducer` that consumes one or more events from `events.jsonl` and maintains an in-memory graph of nodes and edges, persisting snapshots to `<run-dir>/graph.json` and emitting per-event deltas to `<run-dir>/graph.deltas.jsonl`.

#### Scenario: Node taxonomy
- **GIVEN** a sequence of events from `events.jsonl`
- **WHEN** the reducer processes them
- **THEN** it materialises four node kinds: `agent` (one per `agent.spawned`), `url` (one per distinct URL in `browser.visit.url`), `code_ref` (one per distinct `path:start_line-end_line` in `code.cited`), and `signal_source` (one per distinct source identifier in `signal.observed`)
- **AND** each node has a stable id derived deterministically from its key fields (e.g. `agent:<agent-id>`, `url:<sha1(url)>`, `code_ref:<path>:<lines>`, `signal_source:<source>`)
- **AND** node creation is idempotent — repeated events for the same key do NOT duplicate the node

#### Scenario: Edge taxonomy
- **GIVEN** a sequence of events from `events.jsonl`
- **WHEN** the reducer processes them
- **THEN** it materialises four edge kinds:
  - `dispatch` from a parent agent node to a child agent node, sourced from `agent.spawned.parent`
  - `visit` from an agent node to a url node, sourced from `browser.visit`
  - `cite` from an agent node to a code_ref node, sourced from `code.cited`
  - `source_of` from an event reference to a finding node, sourced from `finding.recorded.source_events`
- **AND** each edge carries its source event's `ts` and `event_id` so consumers can replay or filter chronologically
- **AND** edges with identical `(kind, from, to)` tuples are emitted only once per occurrence — counts are tracked on the edge (e.g. `visit_count`) rather than producing duplicate edges

#### Scenario: Snapshot output
- **WHEN** the reducer writes `<run-dir>/graph.json`
- **THEN** the file contains a single JSON object with top-level keys `version` (integer schema version, starting at `1`), `run_id`, `generated_at`, `nodes` (array), `edges` (array), and `cursor` (the `event_id` or byte offset of the last event consumed)
- **AND** the snapshot is a complete, consumer-ready view that does NOT require replaying earlier deltas to reconstruct state

#### Scenario: Delta stream output
- **WHEN** the reducer processes a single event that mutates the graph
- **THEN** it appends one JSON line to `<run-dir>/graph.deltas.jsonl`
- **AND** the line is a single JSON object with keys `ts`, `cursor`, and `ops` (an array of `{op: "add_node"|"update_node"|"add_edge"|"update_edge", ...}` records)
- **AND** events that produce no graph mutation MUST NOT emit empty delta lines

### Requirement: Live consumer runtime

The system SHALL provide `~/.claude/scripts/bin/audit-live` — a local-host runner that ties the reducer to the event stream and serves a browser-friendly feed of the current graph state.

#### Scenario: Tail-and-reduce loop
- **GIVEN** an audit run is in-flight (active.txt resolves a run-id, events.jsonl is being appended to)
- **WHEN** an operator runs `audit-live` from the project root
- **THEN** the runner resolves the active run via the same chain `oss event emit` uses (`AUDIT_RUN_ID` env var → `<project>/docs/audit/active.txt`)
- **AND** spawns a `tail -F events.jsonl | audit-reducer --stream` pipeline
- **AND** updates `<run-dir>/graph.json` after each delta (atomic write via tmp-file + rename)
- **AND** appends to `<run-dir>/graph.deltas.jsonl` for each mutating event

#### Scenario: File-poll transport (default)
- **GIVEN** PRD § 10 Q4 sets the default transport to file-poll
- **WHEN** `audit-live` starts without `--sse` flag
- **THEN** it serves a static HTML page at `http://localhost:<port>/` that polls `graph.json` every 1000 ms (configurable via `--poll-interval`)
- **AND** the page displays a minimal text/JSON view of the current graph (Phase D will replace this with a real viz; this spec ships a dev-grade placeholder)
- **AND** `--port` defaults to `4173`; if occupied, the runner increments until it finds a free port and prints the chosen URL on stdout

#### Scenario: Latency budget
- **WHEN** an event is appended to `events.jsonl`
- **THEN** the corresponding mutation in `graph.json` is observable within 1000 ms (PRD § 11 M4)
- **AND** the runner emits a stderr warning if the reduce-and-write cycle exceeds 1000 ms for any single event, naming the event_id and elapsed time

### Requirement: Partial-JSONL recovery

The reducer SHALL tolerate a malformed final line in `events.jsonl` — treating it as an in-progress write to be retried on the next read — without crashing or skipping the rest of the file. This satisfies PRD NFR4.

#### Scenario: Trailing partial line is retried
- **GIVEN** `events.jsonl` ends with a line that does not parse as JSON (truncated due to a write in flight)
- **WHEN** the reducer reads to EOF
- **THEN** it processes every preceding complete line normally
- **AND** records the byte offset of the start of the malformed line as its cursor
- **AND** on the next poll, re-reads from that offset, accepting the now-complete line

#### Scenario: Malformed-but-not-trailing line is logged and skipped
- **GIVEN** a non-trailing line in `events.jsonl` is unparseable (corruption, not in-flight write)
- **WHEN** the reducer encounters it
- **THEN** it emits a stderr warning identifying the byte offset and the parse error
- **AND** advances past the line without mutating the graph
- **AND** does NOT terminate the run

#### Scenario: Crashed-audit replay
- **GIVEN** an audit terminated mid-run, leaving an `events.jsonl` whose last line is incomplete
- **WHEN** the reducer is invoked one-shot (`audit-reducer --once`) against that file
- **THEN** it produces a `graph.json` reflecting all complete events
- **AND** exits 0 (a partial trailing line is not a fatal condition)

### Requirement: Reducer query helpers in event.sh

The system SHALL extend `scripts/bin/oss-lib/event.sh` with read-side helper functions for reducer consumers — query primitives only; no change to the existing emit path.

#### Scenario: graph_path resolver
- **WHEN** a consumer sources `event.sh` and calls `event_graph_path`
- **THEN** the helper prints the absolute path to `<run-dir>/graph.json` for the current active run
- **AND** uses the same active-run resolution chain as `oss event emit` (AUDIT_RUN_ID env → active.txt)
- **AND** exits non-zero with a stderr diagnostic if no active run can be resolved

#### Scenario: deltas_path resolver
- **WHEN** a consumer sources `event.sh` and calls `event_deltas_path`
- **THEN** the helper prints the absolute path to `<run-dir>/graph.deltas.jsonl` for the current active run
- **AND** the same resolution chain and error semantics as `event_graph_path` apply

#### Scenario: No emit-path regression
- **WHEN** the existing `oss event emit` command is invoked after this spec lands
- **THEN** its behavior, output, exit codes, and validation semantics are identical to before
- **AND** existing audits running against the unmodified emit path observe no functional change
