# Coding samples (RQ2–RQ4): codebook v1

Generated by `src/s08_draw_samples.py` (sampling) and `src/s09_pilot_codebook.py` (automatic features, pilot agreement, recheck set). Seeds and parameters are in `results/numbers.json`, sections `samples` and `pilot`.
Re-running them gives the same files. **Do not edit the generated files by hand.** Copy a template and code in the copy.
This README is written by hand. No script overwrites it.

**Status: codebook v1 is final (frozen 2026-11-20).** No rule changes after this date; double coding uses v1 as written below.

How we got here (all numbers in `results/numbers.json`, section `pilot`):
1. Pilot (30 items, codebook v0): agreement far too low on every field, and taxonomy B failed its stop rule. The team wrote codebook v1.
2. Recheck 1 (10 items with the largest v0 disagreement, v1): requirements improved, implementation did not (`pilot.recheck_v1`). Rules 4a and 4b and two rows of the Rule 4 table were added.
3. Recheck 2 (10 other pilot items, drawn at random, final v1): implementation improved; every remaining disagreement is between adjacent levels, mostly at the none/incidental and incidental/substantial boundaries (`pilot.recheck2_v1`). The team froze the codebook regardless of the result, so that double coding could start before the Nov 22 freeze.

Known limits, for the threats to validity:
- The rechecks are small (10 items each) and reuse pilot items the coders had seen under v0.
- Requirements extent is nearly always `dominant`. With so little variation, κ can be low even when raw agreement is high (the kappa paradox), so we report raw agreement and weighted κ as well.
- Implementation extent has the lowest reliability. Whether to also analyse it on a collapsed two-level scale is decided after double coding, on the double-coding κ, before looking at group differences.

**Next step: double coding.** Each coder copies `double/coding_sheet_TEMPLATE.csv` (v1 columns, including `body_completeness`) and codes in row order, batch 1 (D001–D100) first.

## What the coding is for

The sample holds two groups. Coders do not see which spec belongs to which group.

- **fossil**: the SpecMine flag says fossil (placeholder, 0 revisions) **and** the snapshot text holds the OpenSpec archive placeholder (13,426 specs).
- **edited** ("maintained" in RQ4): living specs with at least one *other edit*, i.e. a revision that is not an archive merge (12,487 specs).

The labels answer two questions:

- **RQ3: what characterizes fossils?** Is a fossil a finished spec whose Purpose nobody filled (the TBD is then mostly harmless), or a half-written spec that was abandoned?
- **RQ4: how do maintained specs and fossils differ?** For example, in how complete their body is, or in how much implementation detail they hold.

To compare the groups, the labels must be **reliable**: two coders working alone must agree (κ ≥ 0.6). Codebook v1 follows one principle: **whatever a script can count, a script counts. Humans judge only what needs judgment, with explicit rules.**

## Sampling (decision brief of 2026-11-12)

- At most 3 specs per repository and group. With a fixed seed, specs are ranked at random. Pilot = ranks 1–15 of each group, double coding = ranks 16–115, LLM-only = the rest.
- Blinding: the sheets do not show the group, and v1 tells coders to ignore the Purpose section, which is where fossils show the TBD.
- The pilot is the **dev set** (codebook, prompt tuning). The double-coding set is the **test set** for the LLM. Never tune the prompt on it.

## Codebook v1

### Fields coded by humans

| Field | Values |
|---|---|
| `is_spec` | `true` / `false`. False if the file is not a spec (empty template, unrelated file). If false, leave the other fields empty and give the reason in `note`. |
| `requirements_extent` | `none` / `incidental` / `substantial` / `dominant` |
| `implementation_extent` | same scale |
| `body_completeness` | `complete` / `skeletal` / `near_empty` |
| `note` | Free text: every hesitation, and every time you opened the GitHub URL. |

### Rule 1: ignore the Purpose section

Skip the `## Purpose` section entirely: do not count it in any extent and do not judge it for completeness. Its state is computed by s09 as `purpose_status`:

| `purpose_status` | When |
|---|---|
| `filled` | the Purpose holds real text |
| `tbd_archive` | the OpenSpec archive placeholder ("TBD - created by archiving change … Update Purpose after archive") |
| `tbd_other` | another TBD, TODO or "to be defined" (e.g. "TBD — restored after delta-sync structural cleanup") |
| `empty` | a Purpose heading with no text |
| `missing` | no Purpose section |

"Finished except the Purpose" (the old `complete_except_purpose`) is now `body_completeness = complete` with `purpose_status` ≠ `filled`.

### Rule 2: body completeness

| Value | Rule |
|---|---|
| `complete` | **Every** requirement has a body (at least one SHALL/MUST sentence or a description) **and** at least one scenario. |
| `skeletal` | There is at least one requirement with a body, but **at least one** requirement is title-only or has no scenario. |
| `near_empty` | No requirement has a body (only headings, titles or the Purpose line). |

Notes:
- A scenario counts if it has a `#### Scenario:` heading and at least one WHEN/THEN (or GIVEN/WHEN/THEN) line. A scenario heading with nothing under it does not count.
- If the spec uses another structure (no `### Requirement:` headings), apply the rule to its equivalent units (numbered requirements, user stories) and say so in `note`.
- "At least one scenario per requirement" follows the OpenSpec spec format as we understand it. [VERIFY against the OpenSpec documentation.]

### Rule 3: extent scale

**Unit: share of the lines with content in the body.** Do not count headings, blank lines, HTML comments (Rule 4b) or the Purpose section. Put each line in one category by its main content (Rule 4). Decide by **share, not by absolute count**, so that short and long specs are rated alike. An estimate is enough ("under a tenth, up to half, or more than half of the body?"); count only when you are unsure between two levels. For very long specs, estimate per section.

| Level | Rule |
|---|---|
| `none` | 0 lines |
| `incidental` | more than 0 and under 10% of the body, **and** no dedicated section |
| `substantial` | 10–50% of the body, **or** a dedicated section (below) even if under 10% |
| `dominant` | more than 50% of the body |

**Floor rule:** a single line is never more than `incidental`, whatever its share (e.g. one line naming a file in a 5-line spec).

**Dedicated section.** A heading whose content is mostly of one category. It counts only if all three hold:
1. It is a real heading (`##`, `###`, …) chosen by the author.
2. It is **outside** the standard OpenSpec structure: `### Requirement:` and `#### Scenario:` headings never count, since every spec has them. Classify the lines inside them one by one, as usual.
3. It has **2 or more lines** of content, mostly of the same category. An empty or one-line section does not count.

| Counts (usually implementation) | Does not count |
|---|---|
| `## Data Model` listing tables and columns | `### Requirement: User login` with one THEN line naming a function: classify that line with Rule 4a |
| `## Architecture`, `## Technical Design`, `## Implementation Notes` | A code block between requirements without its own heading: count its lines |
| `## File Structure` with a directory tree | `## Notes` holding the single line "uses Redis" |
| `### Database Schema` with an SQL block | |

The two extents are rated independently and need not add up to 100% (some lines are neither, e.g. glossary or references).

Fossils are about half as long as edited specs (median body length by group: `results/numbers.json`, `pilot.body_lines_by_group`). The analysis therefore also compares the groups within length strata, using `n_body_lines` from `auto_features.csv`.

### Rule 4: requirement or implementation?

**General rule: what users or other systems can observe from outside is a requirement. How it is built inside is implementation.**

| Content | Category |
|---|---|
| SHALL/MUST statements of behaviour, scenarios (WHEN/THEN), constraints, users and roles | requirement |
| Endpoints, routes, CLI commands and flags, event names, UI text, request and response formats | requirement |
| File names, paths, classes, functions, internal modules | implementation |
| Database tables and columns, storage layout | implementation |
| Named technologies or libraries ("uses Redis", "JWT") | implementation, **unless** the text gives an outside reason ("MUST use X because the host only supports X"): then requirement (a constraint) |
| Code blocks | implementation, **unless** they show example input or output (sample JSON, a CLI call): then requirement |
| Architecture, plans, implementation steps, coding conventions | implementation |
| Content of a prompt the system sends to an LLM or agent | requirement (it is output sent to another system, like UI text or an API format); the code that builds the prompt (e.g. `buildFixPrompt`) stays implementation |
| Reference or link lists ("see also", best-practice links) | neither |

**Rule 4a (added 2026-11-20): lines that name an internal class, function or file.** Use the **black-box test**: *could a tester check this line without reading the code?*
- Yes → **requirement**, even if the line names a class. Example: "PebbleService SHALL open port 8080 and log a WARNING on failure": the open port and the log line are observable.
- No → **implementation**. Example: "The handler SHALL call `plan()` and then update `self._container`": only the code shows this.

This replaces the v1 rule "a THEN line naming a function, file or class is implementation". THEN lines get the same test as all other lines.

**Rule 4b (added 2026-11-20): HTML comments are not body lines.** Lines inside `<!-- … -->` (e.g. `@trace` lists of file paths) do not render and are usually tool metadata. Do not count them in any extent or in the body length; mention them in `note` if they are long. s09 counts them separately (`n_html_comment_lines`).

### Sheet format (mandatory)

- Keep the template's columns and their order, including `item_id` and `note`.
- Write values exactly as in the tables above (`true` / `false`, not `yes` / `no`; `TRUE` / `FALSE` from `label_ui.py` is fine).
- Do not delete, reorder or renumber rows.
- `src/label_ui.py` supports v1 sheets: run `python src/label_ui.py labels/double/coding_sheet_<initial>.csv`.

## Taxonomy B is dropped

Taxonomy B (kind of work: `is_spec_of_work`, `purpose`, `object`) was trialled in the pilot only. Its stop rule required most pilot specs to be specs of work. Both coders rated at most 10% of the pilot specs as specs of work (`results/numbers.json`, `pilot.taxonomy_b_stop_rule`), so B is not coded further. The report states that SpecMine's kind-of-work taxonomy does not fit living specs, which describe the system as it stands.

Leftover delta headers (`## ADDED Requirements` and similar) are counted by s09 (`n_delta_headers`), not coded.

## How to code

1. Each coder copies the template to `coding_sheet_<initial>.csv` in the same folder (e.g. `double/coding_sheet_N.csv`) and codes **alone**. Do not look at the other coder's sheet before both are done.
2. Code in row order. Rows with `batch = 1` come first in the double-coding sheet. They are the first 50 + 50 specs, so if we fall back to 50 + 50, the coded part is still a random sample.
3. For each `specs/<item_id>.md`:
   1. Skim the whole file, skipping the Purpose section. Open the GitHub URL only when the text alone is not enough, and say so in `note`.
   2. `is_spec`: is this a spec at all?
   3. `requirements_extent` and `implementation_extent`: classify the body lines with Rule 4, then rate with Rule 3.
   4. `body_completeness`: check each requirement for a body and a scenario (Rule 2).
   5. `note`: write down every hesitation, e.g. "unsure between incidental and substantial: one short Data Model section".

**Worked example (invented, not in the sample).** A spec with a TBD Purpose, four requirements with two WHEN/THEN scenarios each, and one line "uses `src/auth/session.ts`". Coding: `requirements_extent = dominant` (almost every body line is a requirement or scenario), `implementation_extent = incidental` (one line names a file), `body_completeness = complete` (every requirement has a body and scenarios; the Purpose is ignored). s09 records `purpose_status = tbd_archive`.
