## Groups and sampling (decision brief of 2026-11-12)

- **fossil**: SpecMine flag fossil (placeholder, 0 revisions) **and** the snapshot text holds the OpenSpec archive placeholder (13,426 specs). Every coded fossil holds the tool-written TBD.
- **edited**: living specs with at least one *other edit* (a revision that is not an archive merge), i.e. "maintained" in RQ4 (12,487 specs).
- At most 3 specs per repository and group. With a fixed seed, specs are ranked at random. Pilot = ranks 1–15 of each group, double coding = ranks 16–115, LLM-only = the rest.
- The sheets do not show the group. Blinding is only partial, since fossils still show the TBD Purpose.
- The pilot is the **dev set** (codebook v1, prompt tuning). The double-coding set is the **test set** for the LLM. Never tune the prompt on it.

## What the pilot is for

We do not build categories from scratch. We reuse the taxonomy and judge prompts of the SpecMine paper (its Table III and Appendix F), following instructor comment 1.7, and add one dimension of our own (completeness). The 30-spec pilot has two jobs:

1. **Check the fit.** SpecMine's taxonomy was written for specs that describe *work to be done*. Living specs describe *the system as it stands*. The pilot shows whether the taxonomy still works for them.
2. **Produce codebook v1.** The places where the two coders disagree, and the notes they write, become the definitions and examples of codebook v1, used for the 200 double-coding specs.

## The taxonomies

### Taxonomy A: spec content (pilot and double coding)

A asks: does the text state **requirements** or **implementation**?

| Group | Categories (SpecMine) | Typical form in an OpenSpec spec |
|---|---|---|
| Requirements | problem, behaviour, acceptance, constraints, stakeholders | `### Requirement: … SHALL …`, `#### Scenario:` blocks with WHEN/THEN, limits, who uses the feature |
| Implementation | architecture, plan, code, conventions | file or module names, code snippets, DB schemas, tech stack, implementation steps, naming rules |

SpecMine gives an extent to each category. Our sheet collapses them into **two columns**, `requirements_extent` and `implementation_extent`, each on the extent scale below. The two columns are rated independently. They do not add up to 100%: a spec can be `dominant` on requirements and `incidental` on implementation.

### Taxonomy B: kind of work (pilot only, on trial)

B labels the change a spec is for, with conventional-commit labels: `purpose` (feat / fix / refactor / style / perf) and `object` (docs / test / ci / build / chore). It applies only if the document describes work to be done (`is_spec_of_work = true`, see below). We suspect it fits living specs badly, hence the stop rule.

**Stop rule for B (decision item 1).** B goes into the main coding only if at least 2 labels each occur in at least 15% of the pilot specs **and** most pilot specs have `is_spec_of_work = true`. If B is dropped, "SpecMine's kind-of-work taxonomy does not apply to living specs" is reported as a finding.

### Completeness (our own dimension)

Whether the spec is filled in. Values and definitions are in the field table below. They are ours, not SpecMine's, and the report must say so.

## Fields (codebook v0)

Codebook v1 comes out of the pilot. Until then, use these values:

| Field | Values | Definition |
|---|---|---|
| `is_spec` | `true` / `false` | SpecMine judge A, rule 6: false if the file is not a spec (e.g. empty template, unrelated file). If false, leave the other fields empty and give the reason in `note`. |
| `requirements_extent` | `none` / `incidental` / `substantial` / `dominant` | Share of the document that states requirements: problem, behaviour, acceptance, constraints, stakeholders. Acceptance criteria (scenarios) count as requirements. |
| `implementation_extent` | same scale | Share that states implementation: architecture, plan, code, conventions. |
| `completeness` | `complete` / `complete_except_purpose` / `skeletal` / `near_empty` | See the definitions below. |
| `is_spec_of_work` | `true` / `false` | Pilot only (taxonomy B, rule 5): false if the document describes the system as it is. See the decision guide below. |
| `purpose` | `feat`, `fix`, `refactor`, `style`, `perf`, or `none`; several values separated by `;` | Pilot only (taxonomy B). `none` if `is_spec_of_work = false`. |
| `object` | `docs`, `test`, `ci`, `build`, `chore`, or `none`; separated by `;` | Pilot only (taxonomy B). `none` if `is_spec_of_work = false`. |
| `note` | free text | Anything ambiguous, and every time you opened the GitHub URL. |

**Extent scale** (SpecMine judge A, rule 9): **none** = absent; **incidental** = a line or two in passing; **substantial** = a section or several statements, but not the bulk; **dominant** = most of the document. Mark a category only if you can point to text that shows it. **An empty heading is not evidence.** A `## Purpose` that only holds the TBD adds nothing to requirements.

**Completeness values** (draft definitions, to be confirmed in the pilot):

| Value | Definition |
|---|---|
| `complete` | Every section has content, including a real Purpose. Requirements have bodies and, where OpenSpec expects them, scenarios. Added 2026-11-18 for edited specs without a TBD. |
| `complete_except_purpose` | Requirements and scenarios are filled in. The only gap is the Purpose (usually the tool-written TBD). |
| `skeletal` | The structure is there (headings, requirement titles), but bodies are one-liners or scenarios are missing for most requirements. Applies whether or not the Purpose is filled. |
| `near_empty` | Almost no content beyond headings and the Purpose line. |

## Deciding `is_spec_of_work` (pilot only)

The question is: does the document describe **a change to make** (from the current state to a new one), or **the state the system is in**? SpecMine's rule: if it describes the system as it stands, `is_spec_of_work = false`.

A test that helps: **once the work is finished, does the text become outdated?** A spec of work does: its plan and its "what changes" no longer apply. A description of the system stays true, as long as the system does not change.

| Signals for `true` (work to be done) | Signals for `false` (system as it stands) |
|---|---|
| Delta headers left in the file: `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements` | Requirements stated as standing behaviour, with no reference to a before state |
| Proposal structure: `## Why`, `## What Changes`, `## Impact` | Plain capability description: "The system SHALL …" with scenarios |
| Task lists or checkboxes (`- [ ] 1.1 …`), phases, milestones | No plan, no steps, no order of work |
| Future or imperative wording: "will add", "we need to", "migrate X to Y", "replace", "remove" | Present-tense wording: "the API returns", "users can" |
| An explicit gap: TODO, "not implemented yet", "currently X, should be Y" | Gaps only in the TBD Purpose, which is a tool artefact, not planned work |

Points to keep in mind:

- **SHALL alone is not a signal.** It is normative wording, used both in change proposals and in living specs.
- **The TBD Purpose alone is not a signal.** It was written by the archive tool, not by someone planning work.
- **Mixed documents.** If the spec mostly describes the current system but contains one section of planned work, choose by what dominates and describe the planned section in `note`.
- **No clear signal either way:** choose `false`. A living spec describes the system by definition, so this is the default. Write `default` in `note`, so that we can count these cases. This default is a proposal for codebook v1 and must be confirmed in the pilot.

## How to code

1. Each coder copies the template to `coding_sheet_<initial>.csv` (e.g. `pilot/coding_sheet_N.csv`) and codes **alone**. Do not look at the other coder's sheet before both are done.
2. Code in row order. Rows with `batch = 1` come first in the double-coding sheet. They are the first 50 + 50 specs, so if we fall back to 50 + 50 on Nov 17, the coded part is still a random sample.
3. For each `specs/<item_id>.md`:
   1. **Skim the whole file.** The first line is the item ID and the GitHub URL. Open the URL only when the text alone is not enough, and say so in `note`.
   2. **`is_spec`**: is this a spec at all? If not, `false`, give the reason, and move on.
   3. **`requirements_extent`**: look at Requirement and Scenario blocks, SHALL/MUST sentences, constraints. Estimate their share of the text.
   4. **`implementation_extent`**: look for file names, code, schemas, architecture choices, implementation steps.
   5. **`completeness`**: is the Purpose real or TBD? Do requirements have bodies and scenarios?
   6. **`is_spec_of_work`** (pilot): change to make, or system as it stands? Use the guide above.
   7. **`purpose` / `object`** (pilot): only if step 6 is `true`; otherwise `none`.
   8. **`note`**: write down every hesitation, e.g. "unsure between incidental and substantial: one short Data Model section". These notes are the main input for codebook v1.

**Worked example (invented, not in the sample).** A spec with a TBD `## Purpose`, four requirements with two WHEN/THEN scenarios each, and one line "uses `src/auth/session.ts`". One reasonable coding: `requirements_extent = dominant`, `implementation_extent = incidental` (one line names a file), `completeness = complete_except_purpose`, `is_spec_of_work = false` (it describes existing behaviour, with no delta headers, plan or future wording), `purpose = none`, `object = none`.

## After the pilot

1. When both coders are done, the agent computes agreement per field (Cohen's κ, plus raw agreement), lists the items where the coders disagree, and checks the stop rule for B.
2. The coders meet, resolve the disagreements, and write codebook v1: final values, definitions, inclusion and exclusion criteria, one example per value.
3. Double coding starts with codebook v1.

## Who writes what

The students fill in the human labels. The agent only prepares sheets, computes agreement (Cohen's κ) and runs the LLM pipeline. It never fills in a human label.
