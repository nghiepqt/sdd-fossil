Generated by `src/s08_draw_samples.py` (seed and parameters in `results/numbers.json`, section `samples`).
Re-running it gives the same files. **Do not edit the generated files by hand.** Copy the template and code in the copy.

| Path | Content |
|---|---|

The 259 + 258 `llm_only` rows of `sample_frame.csv` complete the representative samples (374 fossils, 373 edited; 95% confidence, ±5%). Only the LLM labels them, and only if κ ≥ 0.6 on the held-out human labels.

## Groups and sampling (decision brief of 2026-11-12)

- **fossil**: SpecMine flag fossil (placeholder, 0 revisions) **and** the snapshot text holds the OpenSpec archive placeholder (13,426 specs). Every coded fossil holds the tool-written TBD.
- **edited**: living specs with at least one *other edit* (a revision that is not an archive merge), i.e. "maintained" in RQ4 (12,487 specs).
- At most 3 specs per repository and group. With a fixed seed, specs are ranked at random. Pilot = ranks 1–15 of each group, double coding = ranks 16–115, LLM-only = the rest.
- The sheets do not show the group. Blinding is only partial, since fossils still show the TBD Purpose.
- The pilot is the **dev set** (codebook v1, prompt tuning). The double-coding set is the **test set** for the LLM. Never tune the prompt on it.

## How to code

1. Each coder copies the template to `coding_sheet_<initial>.csv` (e.g. `pilot/coding_sheet_N.csv`) and codes **alone**. Do not look at the other coder's sheet before both are done.
2. Code in row order. Rows with `batch = 1` come first in the double-coding sheet. They are the first 50 + 50 specs, so if we fall back to 50 + 50 on Nov 17, the coded part is still a random sample.
3. Read `specs/<item_id>.md`. Open the GitHub URL only when the text alone is not enough, and say so in `note`.

## Fields (codebook v0: taxonomy A and B from SpecMine, Appendix F; completeness is our own)

Codebook v1 comes out of the pilot. Until then, use these values:

| Field | Values | Definition |
|---|---|---|
| `is_spec` | `true` / `false` | SpecMine judge A, rule 6: false if the file is not a spec (e.g. empty template). |
| `requirements_extent` | `none` / `incidental` / `substantial` / `dominant` | Share of the document that states requirements: problem, behaviour, acceptance, constraints, stakeholders. Acceptance criteria count as requirements. |
| `implementation_extent` | same scale | Share that states implementation: architecture, plan, code, conventions. |
| `completeness` | `complete_except_purpose` / `skeletal` / `near_empty` | Our dimension (proposal v2). **Open for codebook v1:** these values were written with fossils in mind. Edited specs without a TBD may need a `complete` value. Agree on this in the pilot. |
| `is_spec_of_work` | `true` / `false` | Pilot only (taxonomy B, rule 5): false if the document describes the system as it is. |
| `purpose` | `feat`, `fix`, `refactor`, `style`, `perf`, or `none`; several values separated by `;` | Pilot only (taxonomy B). |
| `object` | `docs`, `test`, `ci`, `build`, `chore`, or `none`; separated by `;` | Pilot only (taxonomy B). |
| `note` | free text | Anything ambiguous. |

Extent scale (SpecMine judge A, rule 9): **none** = absent; **incidental** = a line or two in passing; **substantial** = a section or several statements, but not the bulk; **dominant** = most of the document. Mark a category only if you can point to text that shows it. An empty heading is not evidence.

**Stop rule for B (decision item 1).** B goes into the main coding only if at least 2 labels each occur in at least 15% of the pilot specs **and** most pilot specs have `is_spec_of_work = true`.

## Who writes what

The students fill in the human labels. The agent only prepares sheets, computes agreement (Cohen's κ) and runs the LLM pipeline. It never fills in a human label.
